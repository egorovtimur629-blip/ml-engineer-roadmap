## Как считаем прогресс

- Прогресс roadmap = число недель со статусом COMPLETED / 52 × 100.
- Прогресс Week 1 по основным задачам = число подтверждённых W1-A–W1-F / 6 × 100.
- Отдельные счётчики: упражнения P01–P20, проверки T01–T10, подтверждённые самостоятельные задачи со ★.
- Оценка Gate — отдельное число от 0 до 100 после проверки; до проверки ставится «—».
- Процент задач, потраченное время и число commits не открывают следующую неделю.

Одна пройденная неделя добавляет примерно 1.92 процентного пункта к доле завершённой программы. Это не оценка профессионального уровня или вероятности трудоустройства.

### Порядок проверки

1. Разрешить точный repository, ветку, каталог и commit SHA, поданный на проверку. Проверить фактический доступ. Если источник недоступен, сообщить о пропуске и запросить необходимое; не писать, что GitHub проверен.
2. Сопоставить файлы и изменения с требованиями текущих Week / Task ID. При повторной проверке изучить diff с предыдущим проверенным commit, затем проверить итоговое состояние кода.
3. Проверить корректность реализации, структуру, читаемость, типы, обработку ошибок и необязательную сложность с учётом текущего учебного уровня.
4. Прочитать tests и проверить, какие реальные требования они покрывают. Если есть CI, сверить проверяемый commit, команду, окружение и результат запуска. Зелёный индикатор CI сам по себе не подтверждает качество тестов.
5. Сверить README с реальными зависимостями, командами и поведением программы. При доступном окружении выполнить разумные проверки на проверяемой версии кода. При невозможности запуска явно отделить чтение от воспроизведения.
6. Для ML-проектов сопоставить training/evaluation code, данные и split, конфигурацию, seed, baseline, метрики, логи, графики и выводы. Проверять честность сравнения и привязку эксперимента к версии кода. Большие данные и модели могут храниться отдельно; в repository нужны их идентификаторы и инструкции доступа.
7. Проверить понимание вопросами по конкретному коду и самостоятельным изменением. Авторство commit и наличие сгенерированного кода не заменяют защиту.
8. Записать доказательства и вывод в PROGRESS.md, обновить связанные задания и только затем принять решение Gate. Ранее проверенная версия сохраняет собственный протокол; новая версия получает новую запись.

### Что записывать о GitHub-доказательстве

Repository URL; ветка и путь; полный commit SHA; для diff — предыдущий проверенный SHA; ссылки на файлы, commit и CI run при наличии; дата; команда; статус проверки; результат; замечания; соответствующие Week / Task ID; ответы защиты.

Способы подтверждения различать явно: «код прочитан», «запущено наставником», «проверен CI run», «лог предоставлен учеником», «ответ на защите». Лог или метрики в repository остаются предоставленными автором данными до проверки их происхождения и воспроизводимости.

Для Week 1 достаточно короткого README и описанных ручных сценариев/assert. Полный блок Git, Linux и pytest остаётся на Week 3. Ссылку на repository и выбранный commit можно предоставить уже для первой проверки.

## Переходы и запрет открытия следующей недели

Разрешённые статусы: NOT STARTED, IN PROGRESS, REVIEW, FAILED GATE, COMPLETED.

1. Назначенная активная неделя получает IN PROGRESS. Остальные остаются NOT STARTED.
2. После подачи материалов на Gate активная неделя получает REVIEW.
3. Если материалов недостаточно для оценки, оставить REVIEW, перечислить недостающие доказательства и не выставлять фиктивные баллы.
4. Если проверка выявила несоответствие требованиям, записать FAIL и FAILED GATE. После исправлений принять новую попытку на REVIEW, сохранив старый протокол.
5. COMPLETED разрешён только после записанного PASS: TOTAL ≥80, обязательный результат действительно работает и понимание подтверждено.
6. Week N, где N > 1, можно открыть только после COMPLETED и подтверждённых PASS всех предыдущих недель. По последовательной программе это означает успешный Gate непосредственно предшествующей недели при сохранении всей цепочки.
7. До PASS на Week 1 Gate Week 2 остаётся NOT STARTED. Не назначать Log Analyzer как следующий обязательный проект и не отмечать начало Week 2.
8. Изменение даты, количество занятий, commits, просмотренных видео и генерация проекта AI не заменяют Gate.

При неожиданном противоречии между таблицей и протоколами не продвигаться дальше, сначала проверить фактические доказательства. Исходный roadmap не редактировать автоматически.
