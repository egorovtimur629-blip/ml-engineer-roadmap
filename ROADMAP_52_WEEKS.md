# ML / Research Engineer — практический план на 52 учебные недели

Версия 1.0 · 15 сентября 2026 · Тимур · проект OpenAI ML Engineer Roadmap.

Правила наставничества: приложенный пользователем главный промпт. Этот файл добавляет программу; текущие задачи, оценки и доказательства хранятся в PROGRESS.md. Первое задание подробно описано в WEEK_01.md.

## Цель и темп

Цель — научиться самостоятельно писать ML-код, обучать и оценивать модели, проверять гипотезы и собирать воспроизводимые системы. В описании позиции [Research Engineer в OpenAI](https://openai.com/careers/research-engineer-san-francisco/) указаны сильное программирование, опыт распределённых систем и исследовательская работа. Это ориентир для содержания программы. Последовательность и сроки ниже — предложенный учебный план, а не официальная программа OpenAI.

52 учебные недели — первый большой этап подготовки. Готовность к конкретной вакансии определяется самостоятельностью, глубиной знаний и проектами; завершение календаря не гарантирует трудоустройство.

**Рабочее допущение: 15 часов в неделю**, пока не известны твой уровень и свободное время. Это 780 часов за 52 учебные недели:

- 10,5 часа — программирование, практические задачи, эксперименты, проверки;
- 3 часа — необходимая теория и решение математических задач;
- 1,5 часа — документация, позднее статьи и papers.

Английский и алгоритмы входят в эти часы. Если есть только 7–8 часов, одна учебная неделя может занимать две календарные. При пробелах в школьной алгебре, функциях, степенях и логарифмах добавляем подготовительные занятия до соответствующего блока. Даты следующих недель назначаем после диагностики. Проверенные навыки можно зачесть через тот же gate, без повторного просмотра курсов.

**Ритм:** небольшая теория → самостоятельная реализация → проверка → исправление → объяснение своими словами. В конце недели остаётся один проверяемый результат. Недели 4, 8, 12 и далее кратно четырём включают обзор блока; если календарь растянулся, отдельный обзор всё равно проводится каждые 4–5 календарных недель.

## Как читать программу

В таблицах указан обязательный минимум. Критерий сдачи строки применяется вместе с общим weekly gate в конце файла. Улучшение метрики не гарантируется: корректный отрицательный эксперимент с анализом может пройти проверку. Код и показатели из учебника не считаются собственным результатом без самостоятельной проверки.

Термины: **baseline** — исходный метод для сравнения; **validation** — данные для выбора решений; **test** — отложенные данные для итоговой оценки; **seed** — начальное состояние генератора случайных чисел; **ablation** — эксперимент с отключением или изменением одного компонента; **eval** — процедура оценки качества.

## Проекты, данные и вычислительный бюджет

Четыре основные работы для портфолио: табличная ML-система, `tiny-lm`, `llm-lab`, исследовательский проект. `study-stats`, математические и RL-упражнения могут жить в одном учебном репозитории. Качество важнее количества репозиториев.

До подтверждения твоего оборудования обязательные упражнения проектируем для небольших данных. Для deep learning сначала замеряем один короткий запуск. Tiny LM можно уменьшить до нескольких слоёв и небольшого контекста; SFT и DPO при нехватке ресурсов выполняем на очень маленькой модели, при необходимости собственной. Это подтверждает понимание метода, но не качество промышленной LLM. Если более крупный эксперимент важен, переносим его до появления ресурсов.

Покупки GPU, подписки и платные API в обязательный план не входят. До расхода денег отдельно согласуется бюджет. Облачные бесплатные лимиты не считаются гарантированными. Выбор внешнего датасета и checkpoint включает проверку описания, лицензии, размера и возможности загрузки на момент начала блока.

Для ранних задач достаточно синтетических данных и небольших встроенных наборов. В каждом проекте фиксируем происхождение данных и правила их использования.

## Weekly gate: одинаковый стандарт на все недели

| Критерий | Баллы | Что проверяем |
|---|---:|---|
| Implementation | 35 | Выполнены требования строки недели; код работает на заявленных входных данных. |
| Code Quality | 20 | Читаемость, разделение ответственности, корректная обработка ошибок; требования усложняются постепенно. |
| Understanding | 20 | Объяснение собственных решений и небольшое самостоятельное изменение/реализация. |
| Experiments / Testing | 15 | Проверки реальных ошибок; позже baseline, split, метрики и сопоставимость экспериментов. |
| Documentation | 10 | Воспроизводимый запуск, зависимости, описание данных, результата и ограничений. |

**PASS = не менее 80/100 + обязательный результат + подтверждённое понимание.** Если отсутствует обязательная часть, обнаружена критическая ошибка или нельзя воспроизвести результат, суммарного балла недостаточно. Неделя остаётся текущей до исправлений.

При нехватке доказательств ставим `REVIEW`, оценку оставляем незаполненной и запрашиваем конкретный недостающий материал. Отсутствие ответа само по себе не является доказательством провала. `FAILED GATE` ставим после проверки, установившей невыполнение условий. При пересдаче сохраняем предыдущую оценку и новую запись.

Пакет для проверки: код или доступ к репозиторию; точный commit/версия; команда запуска; результаты тестов; обязательный артефакт недели; для ML — config, происхождение и split данных, метрики и выводы. Логи ученика маркируем как предоставленные учеником, пока наставник не воспроизвёл запуск. Скриншот интерфейса не заменяет проверку ML-методологии.

Вопросы на понимание: 3–5 коротких вопросов по реальному коду плюс одно небольшое изменение. Если AI написал значимую часть решения, отдельно объяснить её, изменить и заново реализовать ключевой фрагмент самостоятельно. Сначала самостоятельная попытка 20–30 минут, затем небольшая подсказка; при незнании синтаксиса можно сразу открыть документацию.

## Как вести систему в этом проекте

1. Начать с WEEK_01.md и прислать результат первой самостоятельной попытки вместе с ответами о своём уровне и нагрузке.
2. После занятия сообщать: что сделал, ссылку/файл с кодом, команду и результат запуска, что не понял, сколько времени потратил, где помог AI.
3. Наставник сверяет результат с текущей неделей, проверяет доступные доказательства и обновляет PROGRESS.md. Он не повышает статус из-за числа commits или просмотренных видео.
4. Для сдачи написать: «Проверь WEEK N» и приложить пакет доказательств. До ответа на вопросы понимание не считается подтверждённым.
5. После PASS открыть следующую неделю. При FAIL исправить конкретные замечания и принести новую версию. Процент считается только по успешно завершённым неделям.
6. При новом разговоре в этом проекте сначала прочитать актуальные ROADMAP_52_WEEKS.md и PROGRESS.md. Файлы служат источником состояния; если они недоступны, запросить их, а не восстанавливать оценки по догадкам.

Проверка по расписанию может использовать только доступные сохранённые доказательства. Она может запросить код и вопросы к защите; при отсутствии материалов не присваивает PASS. Для проверки GitHub нужен конкретный репозиторий и фактический доступ. В текущем стартовом состоянии репозиторий ещё не указан, запуска кода ученика и проверки навыков не было.

## Правила исследовательского результата

Каждая запись эксперимента: гипотеза → изменение → baseline → данные/split → параметры/seed/бюджет → метрика → результат → интерпретация → следующий шаг. Фиксируем версии, не стираем неудачные запуски. Подобранные на validation решения проверяем на test после выбора финальной конфигурации. После просмотра test повторная настройка требует нового независимого контроля либо явного указания ограничения.

Цель «улучшить coding benchmark на 10%» сначала уточняется: **+10 процентных пунктов** или **+10% относительно baseline**. Например, при baseline 40% это соответственно 50% или 44%. Заранее определяем набор задач, метрику, число попыток, бюджет генерации и процедуру проверки. Сгенерированный код запускается только в изолированной среде с ограничением времени, памяти, сети и доступа к файлам.

Итоговый результат — умение пройти весь экспериментальный цикл и честно защитить выводы. Отсутствие улучшения допускается, если проверка корректна, причины исследованы, а выводы подкреплены данными.
